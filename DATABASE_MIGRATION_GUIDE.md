## Migration Workflow Overview

Our database migration workflow follows these key principles:

1. **Consistent**: All environments (dev, staging, production) use the same migration process
2. **Safe**: Migrations are idempotent (can run multiple times) and include proper error handling
3. **Automated**: CI/CD pipelines handle migrations automatically
4. **Verifiable**: Each migration step includes verification

## Development Workflow

### Setting Up the Environment

First, ensure your development environment is properly set up:

```bash
# From the backend directory
python setup_migration_template.py
```

This sets up our custom migration template that includes best practices.

### Creating a New Migration

When you make changes to the database models:

```bash
# Create a migration that includes your model changes
flask db migrate -m "Description of your changes"

# Review the migration file in migrations/versions
# Edit if necessary to ensure it's idempotent and handles errors

# Apply the migration to your development database
flask db upgrade
```

### Testing Migrations

Before committing a migration:

1. Run the upgrade and downgrade to ensure they work
2. Test data integrity after migration
3. Verify performance on larger datasets if applicable

```bash
# Apply the migration
flask db upgrade

# Test application functionality

# Roll back if needed
flask db downgrade
```

## CI/CD Integration

The CI/CD pipeline automatically handles migrations:

1. **Pull Request Stage**:
   - Runs migrations against a test database
   - Verifies they apply cleanly
   - Checks migration history integrity

2. **Deployment Stage**:
   - Automatically applies migrations before application deployment
   - Verifies database state after migration
   - Rolls back application deployment if migration fails

To enable in your CI/CD pipeline, include the `db_migration_step.yaml` configuration.

## Production Deployment

For production deployments, use our automated deployment script:

```bash
# From the backend directory
./deploy_migrations.sh
```

This script:
- Automatically detects the environment
- Creates backups when possible
- Runs migrations with proper error handling
- Verifies the database state after migration

### Manual Production Deployment

If needed, you can manually run migrations in production:

```bash
# Set environment variables
export FLASK_APP=app:create_app
export FLASK_ENV=production

# Check current database state
flask db current

# View pending migrations
flask db check

# Apply migrations
python deploy_db_migrations.py
```

## Troubleshooting

### Common Migration Issues

1. **Migration conflicts**:
   ```bash
   # Reset migration state to match the database
   flask db stamp head
   ```

2. **Database out of sync with migrations**:
   ```bash
   # Check database state
   flask db current

   # View migration history
   flask db history
   ```

3. **Failed migration**:
   - Check the error logs
   - Restore from backup if necessary
   - Create a hotfix migration to resolve issues

### Emergency Fixes

For emergency database fixes:

1. Create a custom migration that safely fixes the issue
2. Test thoroughly in a staging environment
3. Apply using the deployment script with extra caution

## Best Practices

1. **Always review generated migrations** - Alembic's autogenerated migrations may not catch everything

2. **Make migrations idempotent** - They should be safe to run multiple times

3. **Batch large data migrations** - To avoid locking tables for extended periods

4. **Include both upgrade and downgrade paths** - Always provide a way to roll back

5. **Test migrations thoroughly** - Especially for production critical systems

6. **Back up before migrating** - Always have a recovery plan

7. **Follow naming conventions** - Clear, descriptive migration names help track changes

8. **Document complex migrations** - Leave comments explaining the "why" not just the "what"
